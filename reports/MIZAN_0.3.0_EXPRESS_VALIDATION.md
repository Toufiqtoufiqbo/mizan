# Mīzān 0.3.0 — Express validation

**Date:** 2026-11-13
**Repository:** `Toufiqtoufiqbo/mizan`
**Milestone:** 0.3.0 — cross-framework validation
**Status:** **measured locally. The Express half of the milestone passes.**

> This is a controlled validation against a fixture that was written for this
> milestone. It is **not** a customer deployment, and it is **not** a claim that
> Mīzān supports Express in general. It is one independent implementation of one
> behavioral contract, measured with the raw counts shown below.

## 1. What was validated

| Item | Value |
|---|---|
| Fixture | `tests/fixtures/external_apps/express_store/` |
| Files | `server.js`, `openapi.json`, `package.json`, `package-lock.json` |
| Runtime | Node.js v26.13.1 (also verified on v24.20.0) |
| Framework | Express 4.21.2 - pinned in the lockfile |
| Storage | Node's built-in `node:sqlite` |
| Contract | `tests/fixtures/external_apps/contract/CONTRACT.md` |
| Harness | `mizan.validation.validate_application(..., launch=LAUNCH_EXPRESS)` |
| Budget | 60 requests per variant |
| Result | **the gate passed** — 4/4 variants produced exactly the expected laws |

The fixture is a plausible small store API with its own authentication (opaque
`crypto.randomBytes(32)` bearer tokens in its own database), its own SQLite
database, its own ownership model and its own authorization functions. Its
OpenAPI document is a committed file that describes the actual routes, the
bearer scheme, the path parameter and the required body fields.

### Independence

| Check | Result |
|---|---|
| imports Mīzān | **no** — the only `require(...)` calls are `node:crypto`, `node:sqlite` and `express` |
| calls Mīzān | **no** — the fixture only binds a socket and answers HTTP |
| shares code with the Flask fixture | **no** — different language, different runtime, different auth store, different schema, different OpenAPI source |
| shares code with the FastAPI fixture | **no** — the two were written from the contract, not from each other |
| the only shared artefact | `CONTRACT.md` |

## 4. Negative controls (measured)

The fixture was driven directly over HTTP, without Mīzān, in every variant:

| Control | Result |
|---|---|
| Alice reads Alice's own order | `200` in all four variants |
| Bob reads Bob's own order | `200` in all four variants |
| Alice cannot read Bob's order (`clean`, `write`) | refused (`403`) |
| Bob cannot update Alice's order (`clean`, `read`) | refused (`403`) |
| the listing stays owner-scoped | owners == `{caller}` in all four variants |
| a cross-user read succeeds only in `read`, `both` | confirmed |
| a cross-user write succeeds only in `write`, `both` | confirmed |
| invalid token | `401` |
| missing token | `401` |
| wrong password | refused |
| malformed body (`{"sku": ""}`, `quantity: 0`, `"not-an-object"`) | `400`, no finding |
| unknown order | `404` |

The per-variant HTTP tests are in `tests/test_express_validation.py`
(37 tests, all passing).

## 5. What is different from the FastAPI fixture, and what is not

| Aspect | FastAPI | Express | Does it matter? |
|---|---|---|---|
| OpenAPI source | generated by the framework, fetched over HTTP | a committed file | no - both describe the same routes |
| request body validation | Pydantic, `422` on a bad body | hand-written, `400` | no - neither status becomes a finding |
| cross-user refusal | `404` | `403` | no - Mīzān reports a finding on a `2xx` that returns the object, never on the refusal |
| storage | Python's `sqlite3` | Node's `node:sqlite` | no - both write a standard SQLite file the same attributor reads |
| token shape | `secrets.token_urlsafe(32)` | `crypto.randomBytes(32)` base64url | no - both are opaque and random |
| database location | `root/application.sqlite` | `root/application.sqlite` | no - the launch contract decides it |

The two fixtures produce **the same request accounting and the same findings**.
The difference in the refusal status did not produce a difference in the
outcome - and that is a result, not an assumption.

## 7. What this proves, and what it does not

**Proven here**

- Mīzān's `L2` and `L3` detectors work against a Node.js application whose
  authentication, database, authorization and OpenAPI document were written
  independently.
- The two laws are isolated, and the clean application produces nothing.
- The evidence for each finding is complete and names an owner different from
  the attacker.
- The request accounting separates bootstrap, learning and attack traffic, and
  the budget was not exhausted.

**Not proven**

- universal Express compatibility — one fixture, one Express version, one Node
  version;
- any other JavaScript framework;
- multi-database attribution — this fixture uses SQLite;
- arbitrary black-box HTTP-only identity attribution — the harness is told the
  token→principal map through a documented local test interface;
- L1, L4, L5, L6 or L7 behaviour on this fixture;
- production readiness, or the performance of a real deployment.
