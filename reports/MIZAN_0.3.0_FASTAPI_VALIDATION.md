# Mīzān 0.3.0 — FastAPI validation

**Date:** 2026-11-13
**Repository:** `Toufiqtoufiqbo/mizan`
**Milestone:** 0.3.0 — cross-framework validation
**Status:** **FastAPI half measured locally. Express half not started.**

> This is a controlled validation against a fixture that was written for this
> milestone. It is **not** a customer deployment, and it is **not** a claim that
> Mīzān supports FastAPI in general. It is one independent implementation of one
> behavioral contract, measured once, with the raw counts shown below.

---

## 1. What was validated

| Item | Value |
|---|---|
| Fixture | `tests/fixtures/external_apps/fastapi_store/app.py` |
| Framework | FastAPI 0.162.4 on uvicorn 0.54.0 |
| Contract | `tests/fixtures/external_apps/contract/CONTRACT.md` |
| Harness | `mizan.validation.validate_application(..., launch=LAUNCH_FASTAPI)` |
| Budget | 60 requests per variant |
| Result | **the gate passed** — 4/4 variants produced exactly the expected laws |

The fixture is a plausible small store API with its own authentication (opaque
`secrets.token_urlsafe(32)` bearer tokens), its own SQLite database, its own
ownership model and its own authorization functions. Its OpenAPI document is
generated by FastAPI itself and fetched over HTTP at `/openapi.json`.

### Independence

| Check | Result |
|---|---|
| imports Mīzān | **no** — `ast` scan of `app.py` finds no `mizan` import |
| calls Mīzān | **no** — the fixture only binds a socket and answers HTTP |
| copies the Flask fixture | **no** — different framework, different auth store, different schema, different OpenAPI source |
| shares code with the Flask fixture | **no** — the only shared artefact is `CONTRACT.md` |

## 2. The detection matrix (measured)

| Variant | Expected | Observed laws | Findings | Gate |
|---|---|---|---|---|
| `clean` | none | `[]` | 0 | ✅ |
| `read` | `L2` | `["L2"]` | 1 | ✅ |
| `write` | `L3` | `["L3"]` | 1 | ✅ |
| `both` | `L2`, `L3` | `["L2", "L3"]` | 2 | ✅ |

Every variant was scanned with the same budget and the same identities. The
clean variant produced **zero** findings and sent 16 requests; the vulnerable
variants produced **exactly one** finding each, and the combined variant two.
No variant reported a law it should not have, and no clean variant reported
anything at all.

### Request accounting (raw counts)

| Variant | bootstrap | learning | attack | total | budget | exhausted |
|---|---:|---:|---:|---:|---:|---|
| `clean` | 2 | 11 | 3 | 16 | 60 | no |
| `read` | 2 | 11 | 3 | 16 | 60 | no |
| `write` | 2 | 11 | 3 | 16 | 60 | no |
| `both` | 2 | 11 | 3 | 16 | 60 | no |

The bootstrap is the two logins; the learning phase walks the generated
OpenAPI document; the attack phase is the probes. The budget covers all three
and was never exhausted, so no scan was truncated.

## 3. Finding evidence (verbatim from the run)

### `read` → `L2`

| Field | Value |
|---|---|
| principal | `bob` |
| resource | `orders:ord-4b2ac6f34af4` |
| owner | `alice` |
| method | `GET` |
| endpoint | `http://127.0.0.1:55117/orders/ord-4b2ac6f34af4` |
| status | `200` |

### `write` → `L3`

| Field | Value |
|---|---|
| principal | `bob` |
| resource | `orders:3` |
| owner | `alice` |
| method | `PUT` |
| endpoint | `http://127.0.0.1:55143/orders/ord-4515ec956689` |
| status | `200` |

### `both` → `L2` + `L3`

Both findings above, with `bob` as the principal and `alice` as the owner in
each. The `L2` step is a `GET`; the `L3` step is a `PUT`.

**Every finding passed `validate_finding()`**: it names a principal, a
resource, an action, a reproduction step with a method and a URL, and evidence
that names an owner different from the principal. The read finding's step is a
`GET` — the method actually transmitted — not the method that happened to be in
the traffic log.

## 4. Negative controls (measured)

The fixture was driven directly over HTTP, without Mīzān, in every variant:

| Control | Result |
|---|---|
| Alice reads Alice's own order | `200` in all four variants |
| Bob reads Bob's own order | `200` in all four variants |
| Alice cannot read Bob's order (`clean`, `write`) | refused (`404`) |
| Bob cannot update Alice's order (`clean`, `read`) | refused (`404`) |
| the listing stays owner-scoped | owners == `{caller}` in all four variants |
| a cross-user read succeeds only in `read`, `both` | confirmed |
| a cross-user write succeeds only in `write`, `both` | confirmed |
| invalid token | `401` |
| missing token | `401` |
| wrong password | refused |
| malformed body (`{"sku": ""}`, `quantity: 0`, `"not-an-object"`) | `422`, no finding |
| unknown order | `404` |

The per-variant HTTP tests are in `tests/test_fastapi_validation.py`
(35 tests, all passing).

## 6. What this proves, and what it does not

**Proven here**

- Mīzān's `L2` and `L3` detectors work against an application whose
  authentication, database, authorization and OpenAPI document were written
  independently, in a second framework.
- The two laws are isolated: disabling one check produces one law, disabling
  both produces both, and the clean application produces none.
- The evidence for each finding is complete and names an owner different from
  the attacker.
- The request accounting separates bootstrap, learning and attack traffic, and
  the budget was not exhausted.

**Not proven**

- universal FastAPI compatibility — one fixture, one framework version;
- the Express half of the milestone — not implemented, not run;
- multi-database attribution — both fixtures use SQLite;
- arbitrary black-box HTTP-only identity attribution — the harness is told the
  token→principal map through a documented local test interface;
- L1, L4, L5, L6 or L7 behaviour on this fixture;
- production readiness, or the performance of a real deployment.

The Flask reference fixture still passes its own 12 tests, and the full suite
is green.
