# Mīzān 0.3.0 — cross-framework results

**Date:** 2026-11-13
**Repository:** `Toufiqtoufiqbo/mizan`
**Question:** does Mīzān detect the same authorization violations in
independently implemented applications in two different web frameworks?

**Answer, as measured:** yes, for the two fixtures tested, for the two laws
tested, with no false positive and no false negative across three independent
repetitions of the whole matrix - and with every finding reproduced against the
state the scan left behind.

> These numbers come from two controlled fixtures written for this milestone.
> They are not a measurement of any real application and they are not
> statistically representative of anything else.

## 3. The differences that were investigated

The mission asks for nine areas. Each was exercised by the same scenarios, and
each was compared between the two frameworks.

### 3.1 OpenAPI schema interpretation

| | FastAPI | Express |
|---|---|---|
| source | generated by the framework, fetched from `/openapi.json` | a committed `openapi.json` |
| version | 3.1 | 3.0.3 |
| how it reaches Mīzān | over HTTP, at run time | copied from disk, at run time |

**Result: no difference in the outcome.** The two documents describe the same
routes, the same bearer scheme, the same path parameter and the same required
body fields. The learning phase produced **the same number of requests**
(9) against both. The difference in the document *version* did not matter,
because the learning phase reads `paths`, `requestBody` and `parameters`, which
are identical in 3.0 and 3.1 for these operations.

### 3.2 Authentication header handling

Both applications read `Authorization: Bearer <token>` and reject a missing or
unknown token with `401`. Mīzān sends the token in the same header in both
cases, and the identity map is the same documented interface in both cases: the
harness learns the token→principal mapping from the application's own
`POST /login` and tells the proxy about it.

**Result: no difference.** The two applications use different token generators
(`secrets.token_urlsafe(32)` against `crypto.randomBytes(32)` in base64url),
and neither is a JWT - so the engine's identity-coherence probe (`L1`), which
needs a readable subject, correctly does nothing on either.

### 3.3 Request-body learning

The learning phase builds a sample body from the document's schema. Against
FastAPI it learned `{sku, quantity, note}`; against Express the same three
fields. Against `PUT /orders/{id}` it learned `{status, reason}` in both.

**Result: no difference** - and the bodies are multi-field on purpose, so a
single-field shortcut would not have passed.

### 3.4 Required-field handling

This is where the two applications genuinely differ, and it is worth being
precise about it:

| | FastAPI | Express |
|---|---|---|
| a malformed body | `422` (Pydantic) | `400` (hand-written validation) |
| a missing required field | `422` | `400` |

**Result: no difference in the outcome, and this is the point.** A `400` and a
`422` are both "the request was rejected". Mīzān did not turn either into a
finding - the clean variants produced nothing at all, and the negative controls
assert that a malformed body is refused in both.

### 3.5 Path and parameter handling

FastAPI's path template is `/orders/{order_id}`; Express's is
`/orders/:order_id`. The parameter name was made identical in the Express
fixture so that the two documents describe the same URL, rather than leaving a
cosmetic difference in place to be mistaken for a finding later.

**Result: no difference.** The learning phase resolved the path parameter in
both, and the probes substituted the discovered identifier in both.

### 3.6 Response parsing

Both applications answer with JSON in the same shape (`id`, `owner_id`, `sku`,
`quantity`, `status`, `created_at`), and the listing is `{"orders": [...]}` in
both.

**Result: no difference.** The read probe's check - a `2xx` **and** a body
that actually contains the object - passed in both.

### 3.7 Ownership inference

The owner is read from the `owner_id` field of the object the application
returned, and the probe refuses to blame the owner. In both frameworks the
attacker was `bob` and the owner was `alice`, and the clean variant produced
no finding at all - so the inference was not simply "any other user is an
owner".

**Result: no difference.**

### 3.8 Write attribution

The write probe does not trust the response: it diffs the application's SQLite
file before and after the request and reports the row that actually changed.
Both applications write a standard SQLite file, and the **same**
`SqliteAttributor` read both.

This is the one place where the phase is explicitly **not** testing framework
diversity: the attribution path is database-specific and was shared. The
findings carry `orders:3` in both frameworks - the row key of the SQLite
attributor - and the resource identifier in the `L2` findings is the order id.

**Result: no difference - and the shared dependency is stated rather than
hidden.** See `reports/MIZAN_0.3.0_LIMITATIONS.md`.

### 3.9 Reproduction fidelity

Every finding was replayed against the state the scan left behind: the
application was started again on the same database, the principal logged in
again, and **the recorded step** - the same method, the same path, the same
body - was sent with that principal's own token. Only the port differs,
because the port is chosen per run.

| Framework | Findings | Reproduced | Outcome checked |
|---|---:|---:|---|
| fastapi | 12 | **12** | `L2`: `2xx` and the body contains the object. `L3`: `2xx` and the row is still owned by somebody else. |
| express | 12 | **12** | the same |

**Result: no difference, and nothing was counted that was not reproduced.**

## 4. The one real difference the phase found

Not between the frameworks - **inside** Mīzān.

The benchmark gives every run **unique temporary credentials**. The learning
phase builds its sample body from the OpenAPI document, and the document's
example password is `alice-secret`. When the harness authenticates with the
documented credentials, that example login **succeeds** and its response
(`{"token": ..., "user_id": "alice"}`) contributes one more discovered
identifier to the learning phase - so it sends 11 learning requests. When the
credentials are random, the same request **fails**, one fewer identifier is
discovered, and the learning phase sends 9.

| Credentials | Learning requests | Total | Detection outcome |
|---|---:|---:|---|
| the documented test credentials | 11 | 16 | unchanged |
| unique temporary credentials | 9 | 14 | unchanged |

Two things follow:

1. **the detection outcome did not change** - the same laws were found, with
   the same evidence, in both cases;
2. **the request count depends on the credential scheme, not on the
   framework** - both frameworks behaved identically under both schemes, which
   is exactly what the phase needed to show.

This is a property of the learning phase, not a defect: the probe sends the
document's example, and whether that example is a valid credential is a
property of the deployment. It is recorded here because a benchmark that
measures request counts has to say why they changed.

## 5. Classification of failures

**No failure was observed.** The mission asks for failures to be classified
rather than hidden; there were none in the 24 scenarios, so there is nothing
to classify. For completeness, the classification that *would* have been
applied, and the evidence that each class did not occur:

| Class | What would have shown it | Observed |
|---|---|---|
| Mīzān engine defect | a missing or extra finding, or a finding whose evidence does not hold | none - 24/24 findings, 24/24 reproduced |
| framework-fixture defect | a variant behaving differently from the contract | none - every variant was checked directly over HTTP before Mīzān was involved |
| attribution limitation | a write finding whose row could not be identified | none - the row was identified in every case |
| identity-mapping failure | a principal that could not authenticate | none - 0 missing identities in 24 scenarios |
| unsupported behaviour | a `400`/`403`/`404`/`422` reported as a finding | none - the clean variants produced nothing |
| benchmark-harness defect | a scenario that did not run, ran twice, or reused state | none - 24 distinct workspaces, checked by `check.py` |
| infrastructure failure | a setup error, a crash, an exhausted budget | none - 0 setup errors, 0 errors, 0 budget exhaustions |

A framework is **not** considered validated because its clean case passed. Both
frameworks are considered validated here because all four variants produced
exactly the expected result, and because every finding's evidence passed
validation and replayed.

## 6. How to reproduce it

```console
npm ci --prefix tests/fixtures/external_apps/express_store
python -m benchmarks.cross_framework.run --repetitions 3
python -m benchmarks.cross_framework.check benchmarks/cross_framework/results/results.json
```

The checker is a separate program: the benchmark produces the numbers, the
checker judges them, and the checker fails on a missing finding, an unexpected
finding, an exhausted budget, a setup error, incomplete evidence, or a finding
that could not be reproduced.

The full per-scenario table, with every request, time and memory measurement,
is in `benchmarks/cross_framework/results/results.md` (and `results.json`).
