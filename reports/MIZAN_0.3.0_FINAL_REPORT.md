## 7. L2/L3 evidence and replay results

Every finding names the principal, the owner (who differs from the principal),
the method it actually sent, the endpoint, the resource, the status and the
body.

| Framework | Findings | Evidence validated | Replayed | Outcome of the replay |
|---|---:|---:|---:|---|
| fastapi | 12 | **12** | **12** | `L2`: `2xx` and the body contains the object. `L3`: `2xx` and the row is still owned by somebody else. |
| express | 12 | **12** | **12** | the same |
| **all** | **24** | **24** | **24** | |

Each replay restarted the application **on the database the scan left behind**,
logged in as the finding's principal again, and sent **the recorded step** -
same method, same path, same body. Only the port differs, because the port is
chosen per run.

## 13. Remaining limitations

The full list is in `reports/MIZAN_0.3.0_LIMITATIONS.md`. The short version:

- **not** universal FastAPI or Express compatibility - one fixture each;
- **not** support for every authentication scheme - opaque bearer tokens only;
- **not** multi-database attribution - **both fixtures use SQLite, so the
  attribution path was shared.** This phase tests *framework* diversity, not
  *storage* diversity;
- **not** arbitrary black-box HTTP-only identity attribution - the harness is
  told the token→principal map through a documented local test interface;
- **not** L1, L4, L5, L6 or L7 general support - only L2 and L3 were in scope;
- **not** production readiness, and **not** real-world deployment performance
  - there is no customer deployment, and the benchmark is not statistically
  representative of anything;
- the fixture was **not** copied from the Flask application - it was written
  from the contract, in a different language and a different runtime.
